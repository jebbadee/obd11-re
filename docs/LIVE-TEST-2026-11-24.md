# Live hardware test — 2026-11-24 (Windows 11, Intel AX Bluetooth)

First contact between this project's code and a real OBDeleven dongle, plugged into the car with
ignition ON. Goal: connect from a Windows laptop and read data from the car. **Result: connected
and paired, but no diagnostic data yet — the dongle's command language is still unknown.**

Tags: **V** = verified live in this session, **H** = hypothesis.

## 1. The physical dongle is a first-generation CLASSIC Bluetooth unit (V)

| Property | Value |
|---|---|
| Name | `OBDeleven` |
| Address | `00:0D:19:xx:xx:xx` (OUI `00:0D:19` is registered to a stage-lighting company, not a BT chip vendor → address set by the dongle maker) |
| Transport | Bluetooth **Classic** (BR/EDR), Serial Port Profile (UUID `00001101-…`), **RFCOMM channel 1** |
| Bluetooth LE | **None.** Not seen in LE scans (with and without the classic pairing), direct LE connect by address fails |
| Class of Device | `0x1F00` (uncategorized — an unconfigured-module default) |
| Pairing PIN | **`1234`** (`123456` is rejected) |
| Device ID (DID/PnP) record | none |
| Windows | appears as "Standard Serial over Bluetooth link" COM port once paired |

H: the BT side is a generic UART↔SPP serial module (PIN `1234` + CoD `0x1F00` are typical module
defaults). The module is a transparent pipe; the protocol below lives in the dongle's MCU firmware.
Exact chip unconfirmed — needs a board photo.

**Consequence:** `probe.py` (bleak, BLE-only) cannot reach this dongle. `REPORT.md` covers the BLE
dongles (FFF0 / FFE0 families). This unit is Android-only; iPhones cannot open SPP to it.

## 2. Pairing on Windows (V)

- Windows' own "Add device" fails: it negotiates *display PIN* (shows an 8-digit code the dongle
  can't type) → "Try connecting your device again".
- Working method: WinRT custom pairing restricted to `DevicePairingKinds.ProvidePin`, answering
  `1234` → `classic/classic_repair.py <MAC> 1234`.
- Python's built-in `socket.AF_BLUETOOTH` / `BTPROTO_RFCOMM` works on Windows once paired.

## 3. Protocol probing results (V)

The link opens reliably. Every probe got **no reply**, except one behaviour:

| Sent | Reply |
|---|---|
| `ATZ\r`, `ATI\r`, `AT RV\r`, `ATRV\r\n`, bare `\r` | nothing |
| raw `20 00` (no framing) | nothing |
| single `04`, single `00` | nothing |
| single `0F` | `0F` (within ~100 ms) |
| `0F 04` (empty frame) | `0F` |
| any SLIP frame `0F … 04` from REPORT.md §5 (proto select `[20 00]`, ExtCmd GET_HEALTH_STATUS; scrambled / unscrambled; CRC low-first / high-first / none) | `0F` only |
| `0F` first, wait for echo, then rest of frame | nothing after the echo |
| frame sent byte-by-byte (30 ms gaps) | `0F` only |

So: **the dongle reacts to byte `0x0F` (echoes it) and ignores everything else we know how to say.**
No banner on connect, no idle traffic.

Conclusions:
- REPORT.md §1 hypothesis *"Gen1 Classic dongles are SPP ELM327 ASCII"* is **disproven** for this unit.
- The BLE Gen3 framing (REPORT.md §5) is not accepted as-is either.
- H: `0x0F` is a sync / start-of-frame acknowledgement of an older binary protocol (possibly the
  ancestor of the SLIP-style framing), or a bootloader-style ping. Unknown which.
- Blind probing was stopped deliberately: if the unit is in a firmware/bootloader state, random
  byte sequences could damage it.

## 4. What the code needs next (open questions)

1. **The gen1 handshake** that follows (or replaces) the `0F` echo. Best sources, in order:
   - Bluetooth HCI snoop log from an **Android** device running the OBDeleven app against this dongle
     (Developer options → "Enable Bluetooth HCI snoop log"; pull via `adb bugreport`).
   - Decompile an **older** OBDeleven APK (pre-BLE era) and find the `createRfcommSocket` path;
     the current v2.16 APK in REPORT.md is BLE-focused.
2. Public search (2026-11-24) found **no** published gen1 protocol, code, or capture.
   A 2020 security write-up (Pen Test Partners, "OBDeleven vulnerability") reports the app downloads
   its function commands from the vendor API and that UDS seed/key runs inside the dongle.

## 5. Route being tried for the capture: the car's Android head unit (in progress)

The car has an aftermarket Android 10 head unit (Topway **TS18** platform). It **paired with the
dongle successfully using PIN `1234`**, so it can host the OBDeleven Android app and record an HCI
snoop log. Blocker: ADB is locked.

- Head unit USB port is host-only → no USB ADB.
- Network ADB (TCP 5555) refused until enabled.
- Developer options needs a code. Reported for TS10/TS18 (forums, unverified on this unit):
  `7890` + current 24-hour hour of the **unit's** clock (e.g. `789020`), then a second passcode
  when toggling USB debugging: `john@tw-desktop`. Alternative: Factory settings `123456`/`8888`
  → Engineer Mode → Debug & Log → ADB shell → `setprop service.adb.tcp.port 5555`.
  Sources: github.com/StarMusa88/TopWay-Android-Headunit-ADB-Guide, XDA thread
  "TS18 devices branded Topway" (pages 4, 10, 13).

## 6. Tools added in `classic/`

| Script | What it does |
|---|---|
| `classic_scan.py` | lists classic + LE devices Windows can see (paired / unpaired) |
| `classic_info.py <MAC>` | name, connection state, class of device, pairing state |
| `classic_repair.py <MAC> <PIN>` | unpair (if paired) and re-pair supplying the PIN |
| `classic_try.py <MAC> [ch]` | ASCII/ELM probes over RFCOMM |
| `classic_bin.py <MAC>` | REPORT.md binary frames over RFCOMM, decodes any reply |
| `classic_char.py <MAC>` | which bytes trigger the `0F` reply |
| `classic_sync.py <MAC>` | handshake-timing variants around the `0F` echo |
| `le_after_unpair.py <MAC>` | drops the classic pairing and looks for an LE side |

All need `pip install bleak` (pulls the `winrt` packages) on Windows 10/11, Python 3.10+.
